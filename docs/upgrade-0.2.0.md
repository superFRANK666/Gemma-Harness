# 0.2.0 本地模型性能与可靠性升级

本轮以用户提供的本地 Harness 问题清单为审查线索，检查实际实现，并修复已经复现的工程缺陷。保留 Rust／Tauri、LM Studio 和受管 llama.cpp，不增加多智能体推理，不自动替换模型或改用云端。

## 对问题清单的判断

上下文中的工具定义、历史输出、图像和重复模型调用确实需要单独预算；不同推理 API 的功能也不能只凭“OpenAI 兼容”来判断。这两点与本项目直接相关。

但执行型 Agent 与模型能力评测应分别处理。本项目不实现 MMLU、BLEU 或 ROUGE。EleutherAI 的 [LM Evaluation Harness](https://github.com/EleutherAI/lm-evaluation-harness) 本身支持本地 Hugging Face、GGUF 等后端；其 [任务配置](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/task_guide.md) 区分生成与似然任务，不能把所有选择题概括为读取 A/B/C/D 四个单 token 的概率。

“超过 8K 必然失效”“必须 BF16”“必须改用 vLLM”都不能作为本项目的通用前提。长上下文和量化质量需要在指定模型、模板、后端及硬件上验证。[vLLM 的量化支持表](https://docs.vllm.ai/en/stable/features/quantization/index.html) 也区分硬件与量化实现；更换服务不自动提升所有本机配置。项目维持 8K 的保守起点，并读取 LM Studio 实际加载值，不把起始配置当成模型质量的理论上限。[Ollama 官方也提供工具循环](https://docs.ollama.com/capabilities/tool-calling)，不能仅凭产品定位断言其无法接入 Agent。

## 已实施的改进

| 范围 | 已复现的问题 | 0.2.0 行为 |
|---|---|---|
| 推理调度 | 原先按完整 URL 加锁，锁覆盖整轮；诊断绕过锁 | 按服务 origin 归一化，常见本机地址别名共用额度；对话、摘要、诊断共用单生成准入；工具执行释放额度，排队可取消 |
| 历史恢复 | 每次恢复解析全部旧日志、终端活动和压缩前历史 | SQLite 直接读取最新压缩检查点和后续消息；按主键读取会话，原始目标及历史搜索独立查询 |
| 上下文计量 | 为计算预算复制、序列化图像 base64 | 遍历借用数据，图像只计图像余量；真实服务端 usage 可提高本轮估算余量，仍明确标记为估算 |
| 历史摘要 | 截取 JSON 开头可能产生残缺结构，并遗漏后续测试结果 | 摘要输入是有效 JSON，工具输出保留头尾；保留用户约束，完整摘要请求也经过校准后的预算检查 |
| 工具定义 | 可选工具组持续累计，空搜索可能载入全部工具 | 每次至多六个可选工具，替换上一组；支持按 MCP 原始名称／描述检索，遗漏工具用更精确查询加载 |
| 工具输出 | 多段 MCP 文本每段各有 6K 上限，累计无界 | 多段文本共用 6K 字符预览预算；大文本写入内容寻址 artifact；视觉未启用时收到的原始图片仍先归档 |
| 重复失败 | 同一失败工具可持续消耗 48 步 | 相同名称、参数失败三次停止本轮；成功编辑／修复后允许重新验证；原有整体步数上限保留 |
| 模型协议 | 裸 DONE 可掩盖缺少终止状态；Responses 多段输出合并不完整 | 严格检查完成状态，按索引合并、去重并检测冲突；未完整确认的调用不会执行 |
| 参数兼容 | 默认可选参数被老服务拒绝后直接失败 | 只在明确 400／422 指向可选字段时有界协商；不删除工具、模型、输出限额或 Responses 的 `store:false`，不伪造 usage |
| Worker／MCP | 写入不受取消／期限控制，先读无限行再检查长度，故障连接可复用 | 整次交换具有取消和期限，读取阶段限额，协议失效后清理进程；已发送动作丢失回执时标记结果待确认 |
| 终端完整性 | 输出捕获失败可被吞成空字符串，收尾任务可能遗留后台 | 输出完成状态与命令退出码分开报告；收尾期限后中止并回收任务，保留明确捕获错误 |
| GUI | 每个分片重绘所有 Markdown／工具 JSON，聊天强制滚到底 | 批量刷新流式分片，记忆化历史卡片，展开时才渲染工具详情，按需显示较早活动；阅读历史时暂停跟随 |
| 可观测性 | 已有底层耗时未显示，旧会话用量可能残留 | 显示排队、首响应、真实用量及请求吞吐；预算拆分包含工具定义和输出预留，切换会话清除旧指标 |

参数兼容修复参考 [LM Studio API 更新记录](https://lmstudio.ai/docs/developer/api-changelog)。Responses 的完成和分片状态按公开 API 类型处理，不通过猜测补造成功状态。

## 如何评估改进

`cargo run --release -p harness-core --example performance_probe` 在独立临时目录创建合成历史，以同一进程复现旧算法并比较当前实现。结果为七次中位数，记录在 [性能探针结果](performance-upgrade-20261109.json)。它测量 Harness 的历史投影与图像预算计算开销，不测 Gemma 的生成质量、真实首 token 或整机内存，不应把探针倍率宣传为模型加速。

GUI 的 `tok/s` 使用服务端报告的输出 token 数除以请求总耗时，包含预填充和网络；它不是纯解码速率。没有真实 usage 或请求失败时不显示该速率。上下文的本地数值继续标为估算，后端用量才标为实测。

最新工程测试、安装包及限制见 [验收记录](acceptance.md) 和 [结构化验证结果](verification.json)。上一轮原生工作台验收的证据仍保留原构建校验值，不能拿旧构建的交互结果替代本轮新功能测试。

## 仍需真实环境验收

用户 Windows LM Studio 暂不可达；指定量化版本的工具选择、模板、projector、任务成功率和吞吐未知。macOS 的 Harness 自身桌面权限，以及 Windows／Linux 交互桌面与安装包实机验收仍未完成。估算器不是 Gemma tokenizer；origin 准入也无法控制本程序之外的客户端，或识别反向代理背后不同地址共用的 GPU。正式签名／公证仍需要发行证书。

GUI 的历史首屏限制控制的是 DOM 渲染，打开会话时仍读取完整事件。极长会话在 GUI 的源数据分页，以及原始日志／artifact 的磁盘保留策略仍可继续优化；本轮不宣称整段会话或磁盘占用已经有界。
